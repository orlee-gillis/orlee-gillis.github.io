About me

Documentation as a product, not an afterthought

I'm currently a Senior Technical Writer on the support enablement side at XM Cyber, where I own the documentation for the core CTEM platform. Before that I managed documentation at SysAid, and earlier I wrote for Check Point, IT Central Station and Cyberint.

My background is in teaching, and it shows in how I write: I start from what the reader is trying to get done, then work out the shortest honest path to it. I also work with LLM and MCP documentation, and I use AI tools every day as part of how I draft and edit.

I'm moving toward roles where documentation, enablement and customer operations meet, where the question is not just "is this page well written?" but "did it help the business?"

The project

Ridgeline documentation

Ridgeline is a fictional security product. I invented it so I could show a complete documentation set without sharing anything confidential from my employers.

The docs site is the real thing, though. Every page is a Markdown file in a Git repository, every change goes through a pull request, and the site rebuilds and deploys automatically when a change is merged.

The newest section covers an Unused Access feature, written with an AI-assisted workflow under human editorial control. The AI drafts, flagged problems and my edits are all kept in the open.

How it works

From a Markdown file to a live page in four steps

  1. 01
    Write

    Pages live as Markdown in a Git repository, next to the history of every change.

  2. 02
    Review

    Each change is a pull request, so edits are visible and discussed before they ship.

  3. 03
    Check

    Automated builds block any merge that would break the site.

  4. 04
    Publish

    Merging to the main branch deploys the new version to GitHub Pages automatically.
